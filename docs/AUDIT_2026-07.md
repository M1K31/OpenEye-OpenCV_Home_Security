# OpenEye Security & Architecture Audit

**Prepared for:** Smart Industries LLC
**Date:** 21 July 2026
**Scope:** 390 tracked files — 64,930 lines Python, 30,697 lines JavaScript/JSX
**Branch audited:** `fix/camera-discovery-and-ws-rce`

---

## Executive Summary

OpenEye is a substantial, feature-complete surveillance platform: 30 API route modules, a
multi-stage hardened Dockerfile, five CI workflows, 38 test files, alembic migrations, and a
themed React frontend. The engineering breadth is real and the security *scaffolding* is
genuinely good — SQLAlchemy ORM throughout (no SQL injection found), a non-root container
user, per-endpoint rate limiting, security-headers middleware, and signal-based graceful
shutdown.

The problem is not capability. It is that several load-bearing safety mechanisms are
present but non-functional, which produces false confidence.

Three findings dominate everything else:

1. **The test suite has not run for some time and CI cannot report failure.** All 38 test
   files fail at collection because `ecosystem_auth` is imported unguarded. CI masks this
   with `continue-on-error: true` *and* `|| echo`. Every green checkmark in the repository
   history is uninformative.
2. **A LAN attacker can become admin.** `SECRET_KEY` silently falls back to the constant
   `"dev-secret-key-change-in-production"` outside production, while the service binds
   `0.0.0.0`. Anyone on the network can forge an admin JWT. Until the `eval()` fix landed
   this chained to unauthenticated remote code execution.
3. **A face-recognition product ships with no privacy policy.** Biometric templates are
   special-category data under GDPR Article 9, and Illinois BIPA carries statutory damages
   per violation. This is a legal exposure, not a documentation gap.

Recommended posture: **not ready for external beta.** Roughly two focused weeks of
remediation gets there. Nothing found is architecturally fatal.

## Phase 1 — Code Review & Security Audit

### F-02 (Critical) — Hardcoded secret key enables admin impersonation

`backend/core/auth.py:36-42`

```python
if not SECRET_KEY or SECRET_KEY in ["your-secret-key", "dev-secret-key"]:
    if os.getenv("ENVIRONMENT", "development") == "production":
        sys.exit(1)
    logger.warning("Using weak SECRET_KEY - DEVELOPMENT ONLY")
    SECRET_KEY = "dev-secret-key-change-in-production"   # <-- published constant
```

The guard only fires when `ENVIRONMENT=production` is explicitly set. The default is
`development`, so the shipped launchd/systemd services — which bind `0.0.0.0` — run with a
key published in this repository. Forging `{"sub": "admin"}` is trivial.

The `ENVIRONMENT` variable is also absent from the generated launchd plist entirely, so the
production branch is unreachable in the default install.

**Fix — fail closed, and derive a per-install key rather than depending on the operator:**

```python
SECRET_KEY = os.getenv("SECRET_KEY")

if not SECRET_KEY or SECRET_KEY in _KNOWN_WEAK_KEYS:
    # A network-listening service must never fall back to a published constant.
    # Generate a per-install key once and persist it with owner-only permissions.
    key_file = Path(os.getenv("OPENEYE_DATA_ROOT", Path.home() / ".local/share/openeye")) / "secret.key"
    if key_file.exists():
        SECRET_KEY = key_file.read_text().strip()
    else:
        SECRET_KEY = secrets.token_hex(64)
        key_file.parent.mkdir(parents=True, exist_ok=True)
        key_file.write_text(SECRET_KEY)
        key_file.chmod(0o600)
        logger.warning("Generated a new SECRET_KEY at %s", key_file)
```

Rotating the key invalidates existing sessions — expected and acceptable.

### F-01 (Critical, fixed) — Arbitrary code execution via WebSocket

`backend/api/routes/websockets.py:164` passed every client frame to `eval()`. Any client
reaching the socket could execute arbitrary Python. Combined with F-02 this was a
network-to-RCE chain requiring no valid credentials. Replaced with strict `json.loads`
in commit `3a53d9e`.

### F-08 (High) — CORS wildcard with credentials

`backend/main.py:158-161`

```python
allow_origins=["*"] if CORS_ALLOW_ECOSYSTEM else CORS_ORIGINS,
allow_credentials=True,
```

`CORS_ALLOW_ECOSYSTEM` defaults to `false`, which contains the blast radius — but when
enabled, Starlette reflects the requesting origin while permitting credentials. Any website
the user visits can then drive the authenticated API. Replace the wildcard with an explicit
ecosystem origin allowlist; never pair `*` with `allow_credentials=True`.

### F-13 (Medium) — Untrusted deserialization

`backend/core/face_recognition.py:416` calls `pickle.load()` on the encodings file. Anyone
who can write that path achieves code execution. Face encodings are plain numpy arrays —
use `numpy.save`/`numpy.load` with `allow_pickle=False`, or serialize to JSON.

### F-14 (Medium) — Error handling and logging hygiene

218 `print()` calls in backend code bypass the logging configuration entirely — output
vanishes into launchd's stdout log without level, timestamp, or module. 7 bare `except:`
clauses will swallow `KeyboardInterrupt` and `SystemExit`, actively interfering with the
graceful-shutdown path. 11 `except Exception: pass` blocks discard errors silently.

### F-15 (Medium) — Module size

`backend/api/routes/ecosystem.py` is 1,885 lines; `camera_manager.py` 1,355; `users.py`
1,341. On the frontend, `RecordingsPage.jsx` is 1,317 lines. These exceed what can be
reviewed or tested effectively and concentrate merge conflicts.

### Clean results

Worth recording explicitly: **no SQL injection** (parameterized ORM throughout), **no
`shell=True`**, **no `os.system`**, and **no `dangerouslySetInnerHTML`/`innerHTML`** in the
React tree. `.gitignore` correctly excludes `.env`, `*.db`, `venv`, media directories; only
`.env.example` is tracked. No live credentials found in tracked source — the hits in
`integrations/*.py` are placeholder values inside `__main__` demo blocks.

## Phase 2 — Dependency & Framework Health

### F-05 (High) — npm audit: 16 vulnerabilities

Actual `npm audit` output, not simulated:

| Severity | Package | Issue |
|----------|---------|-------|
| Critical | `vitest` | Arbitrary file read/execute when UI server listens |
| Critical | `@vitest/ui`, `@vitest/coverage-v8` | Transitive via `vitest` |
| High | `axios` | `NO_PROXY` normalization bypass → SSRF |
| High | `react-router`, `react-router-dom`, `@remix-run/router` | XSS via open redirect |
| High | `vite` | Path traversal in optimized-deps `.map` handling |
| High | `rollup` | Arbitrary file write via path traversal |
| High | `ws` | Uninitialized memory disclosure |
| High | `form-data` | CRLF injection in multipart field names |
| High | `picomatch`, `flatted` | Method injection; unbounded-recursion DoS |
| Moderate | `postcss`, `follow-redirects` | XSS; auth-header leak on cross-domain redirect |

**Every one reports `fixAvailable` with no semver-major bump.** `npm audit fix` resolves the
entire set. This is the highest value-to-effort item in the audit.

### F-06 (High) — No dependency pinning

`requirements.txt` contains 91 lines and **zero** `==` pins — every dependency is `>=`.
There is no `requirements.lock`, no `poetry.lock`, no hash verification. Two installs a week
apart produce different dependency trees, which makes any bug report unreproducible.

Compounding this, `.github/workflows/ci.yml:56`:

```yaml
pip install "ecosystem-auth @ git+https://github.com/M1K31/appEcosystem.git#subdirectory=auth/python"
```

An unpinned git URL with no commit SHA. Whatever is on that default branch at build time
enters the dependency tree — a textbook supply-chain exposure.

**Fix:** adopt `pip-compile` (pip-tools), commit `requirements.lock` with hashes, install via
`pip install --require-hashes`, and pin the git dependency to a commit SHA. `package-lock.json`
already exists on the frontend and should be enforced with `npm ci` rather than `npm install`.

### Framework currency

React 18.2, Vite 7.2, FastAPI ≥0.104, SQLAlchemy 2.0 — all current, no deprecated-API usage
found. `numpy<2.0` and `opencv<4.11` are deliberately constrained for dlib/torch
compatibility, which is correct but should be revisited when dlib publishes numpy-2 wheels.
Neither `pip-audit` nor `safety` is installed or wired into CI; Python dependencies have
effectively never been vulnerability-scanned.

## Phase 3 — UI/UX & Apple HIG Compliance

### F-09 (High) — Trademarked theme identifiers

`frontend/src/context/ThemeContext.jsx:16-26` defines nine themes whose internal codes are
transparent references to DC Comics characters:

```js
MAN_OF_STEEL: 'sman',        DARK_KNIGHT: 'bman',
AMAZONIAN_DEMIGOD: 'wwoman', HERMES: 'fman',
KING_OF_ATLANTIS: 'aman',    LANTERN: 'glantern',
CYBORG: 'cyborg',
```

The display names are paraphrased, but `sman`/`bman`/`wwoman`/`fman`/`aman`/`glantern`
are not ambiguous, and the paraphrasing itself evidences awareness. For a Smart Industries
commercial product — particularly one targeting the App Store, which screens for IP
infringement — this is a real takedown and rejection risk. Rename to descriptive palettes
(`midnight`, `crimson`, `abyss`) and drop the character codes.

### F-11 (Medium) — No light/dark mode

`prefers-color-scheme` appears **zero times** across 1,960 lines of theme CSS. The system
ships nine decorative themes but cannot follow the operating system's appearance setting —
the single most visible HIG expectation on Apple platforms, and a baseline expectation on
every modern platform.

The existing architecture is close: `ThemeContext` already stamps a class on
`documentElement`, which is the right mechanism. What is missing is a light/dark axis
*orthogonal* to the decorative theme.

**Recommended token architecture:**

```css
/* Semantic tokens — components consume only these, never raw colors */
:root {
  --surface-primary:   #ffffff;
  --surface-secondary: #f5f5f7;
  --text-primary:      #1d1d1f;
  --text-secondary:    #6e6e73;
  --accent:            #0071e3;
  --border-subtle:     rgba(0, 0, 0, 0.12);
}

/* Follow the OS by default */
@media (prefers-color-scheme: dark) {
  :root:not([data-appearance]) {
    --surface-primary:   #1c1c1e;
    --surface-secondary: #2c2c2e;
    --text-primary:      #f5f5f7;
    --text-secondary:    #98989d;
    --accent:            #0a84ff;
    --border-subtle:     rgba(255, 255, 255, 0.16);
  }
}

/* Explicit user override always wins over the OS signal */
:root[data-appearance="dark"]  { /* dark values */ }
:root[data-appearance="light"] { /* light values */ }

/* Decorative themes override only the accent axis, and stay
   independent of the light/dark axis. */
.crimson-theme { --accent: #d7263d; }
```

`ThemeContext` then manages two independent values — `appearance` (`system`|`light`|`dark`)
and `theme` (decorative) — writing `data-appearance` on `documentElement` and subscribing to
`matchMedia('(prefers-color-scheme: dark)')` for live OS changes.

Also note `ThemeContext.jsx:51` does `document.body.className = ...`, which **clobbers every
other class on `<body>`**. Use `classList.add`/`remove`.

### F-12 (Medium) — Accessibility

Against 201 interactive elements there are 24 `aria-label`s and 20 `alt` attributes. 29
`<div onClick=...>` handlers are not reachable by keyboard and expose no role — a WCAG 2.1
Success Criterion 2.1.1 (Keyboard) failure. Convert to `<button>`, or add
`role="button"`, `tabIndex={0}`, and an `onKeyDown` handler.

Not yet verified and requiring device testing: 44×44pt minimum touch targets, Dynamic Type
support, and colour-contrast ratios across all nine themes (decorative palettes are a common
source of contrast failures).

### F-16 (Low) — Repository hygiene

`frontend/src/themes.css.corrupted` is **tracked in git**. A stray `=1.3.0` file at the
project root is the residue of an unquoted `pip install pkg>=1.3.0`.

## Phase 4 — DevOps, Lifecycle & Memory Management

### What is already correct

Genuinely good, and worth not regressing:

- `backend/main.py:106-121` installs real `SIGINT`/`SIGTERM` handlers with re-entrancy
  protection, and the shutdown path stops the statistics broadcaster explicitly.
- `Dockerfile` is multi-stage (node builder → python builder → slim runtime), runs as
  non-root `USER openeye`, and declares a `HEALTHCHECK`.
- `install-local.sh` correctly snapshots code onto the internal disk, with an accurate
  comment explaining that macOS TCC denies launchd-spawned binaries access to `/Volumes`
  and that an external volume vanishing mid-run causes `SIGBUS` in mmap'd C extensions.
- venv placement is deliberate and documented (`OPENEYE_VENV`, `check-venv-location.sh`).

### F-10 (High) — The launchd agent can never access a camera

The generated plist runs a bare interpreter:

```xml
<string>$VENV/bin/python3</string><string>-m</string><string>uvicorn</string>
```

macOS grants camera access only to a process it can attribute to an application bundle
carrying `NSCameraUsageDescription`. A launchd-spawned interpreter has no bundle, no usage
description, and no GUI session — TCC returns *not determined*, denies, and **never displays
a prompt**. Every macOS install therefore finds zero USB cameras.

Partially addressed: discovery now detects and explains the denial (commit `3a53d9e`), and
the installer warns at install time. The durable fix is to ship a minimal `.app` wrapper
whose `Info.plist` declares `NSCameraUsageDescription` and have launchd start *that*.

### F-19 (Medium) — Runtime is a snapshot, not a link

`$APP_DIR` is an `rsync` copy of the repository. Editing repository source has no effect on
the running service until the installer is re-run. This is a defensible production choice,
but it will repeatedly mislead developers and alpha testers debugging their own installs.
Recommend a documented `--dev` install mode that symlinks instead, plus a startup log line
stating which snapshot revision is running.

### Uninstall

`uninstall.sh` and `uninstall-keep-data.sh` both exist and correctly separate code removal
from data removal — good practice for a product holding irreplaceable recordings. Both need
an end-to-end test on a clean machine before beta.

## Phase 5 — Documentation

`README.md`, `usage.md`, `todos_changelog.md`, `CHANGELOG.md`, `DOCKER.md`,
`docs/API_REFERENCE.md`, `docs/USER_GUIDE.md`, and `docs/UNINSTALL_GUIDE.md` already exist
and are reasonably maintained — 12 markdown files are tracked. The requested Phase 5
artifacts are largely present; they need refresh, not creation. Only 14 TODO/FIXME markers
exist across ~95k lines, which is unusually disciplined.

### F-20 (Medium) — Documentation is tracked by allowlist, so new docs vanish silently

`.gitignore:106` ignores `*.md` repository-wide, then re-admits individual files with
root-anchored negations (`!/README.md`, `!/CHANGELOG.md`, `!/DOCKER.md`, …). The
consequence is that **any markdown file not explicitly allowlisted is silently excluded from
version control**. `ECOSYSTEM_GUIDE.md` and `CLAUDE.md` are already casualties — both exist
on disk and neither is in the repository. This audit file required `git add -f`.

The comment at `.gitignore:101` asserts "docs/ is NOT gitignored", which the rule at line
106 contradicts. Invert the policy: track markdown by default and ignore only the specific
scratch directories (`.superpowers/`, `archives/`, `openeye_backup*/`).

### F-04 (Critical) — No privacy policy

No privacy policy exists anywhere in the repository. For a product that computes and stores
**facial recognition templates**, this is the most serious non-code finding in this audit.

- **GDPR Article 9** classifies biometric data used for identification as special-category
  data, requiring explicit consent and a documented lawful basis.
- **Illinois BIPA** requires written consent before collecting biometric identifiers and
  provides a private right of action with statutory damages *per violation* — the statute
  behind several nine-figure settlements.
- **Texas CUBI** and **Washington HB 1493** impose comparable duties.
- **App Store Review Guideline 5.1.1** requires a privacy policy link for any app accessing
  camera or biometric data; submission without one is rejected.

The policy must state: what biometric data is derived and retained, retention duration and
deletion mechanism, that processing is local-only (a genuine competitive strength worth
stating plainly), what leaves the device via integrations (MQTT, webhooks, Nest, Home
Assistant), and the operator's own obligation to notify recorded individuals.

### F-18 (Low) — Attribution

`LICENSE` reads `Copyright (c) 2025 Mikel` — no surname, no entity. For work owned by Smart
Industries LLC this should read `Copyright (c) 2025-2026 Smart Industries LLC`. Source
headers say `Copyright (c) 2025 Mikel Smart`, so ownership is currently ambiguous between
the individual and the company across the codebase.

## Phase 6 — Production Readiness Plan

### F-03 (Critical) — Restore the safety net first

Nothing else should be attempted until tests run, because no other change can be verified.

**Cause 1 — collection failure.** `backend/api/routes/ecosystem.py:24` imports
`ecosystem_auth` at module scope. It is not in `requirements.txt`. Importing
`backend.main` therefore fails, so `conftest.py` fails, so all 38 test files fail to
collect. `backend/api/routes/settings.py:278` already demonstrates the correct pattern —
import lazily inside the handler and return `501` when absent. Apply that to `ecosystem.py`,
or declare the dependency properly.

**Cause 2 — CI cannot fail.** `.github/workflows/ci.yml:75`:

```yaml
pytest tests/ ... -x --ignore=tests/e2e || echo "Some tests failed - check test output"
continue-on-error: true
```

Both `|| echo` and `continue-on-error: true` are present, either of which alone guarantees a
green job. Lint (line 66) and the step at line 85 are likewise `continue-on-error`. Remove
all three so the pipeline can report truth.

### Roadmap

**Week 1 — Stop the bleeding**
1. Fix `ecosystem_auth` import; get all 38 test files collecting (F-03).
2. Remove every `continue-on-error` and `|| echo` from `ci.yml` (F-03).
3. Replace the `SECRET_KEY` fallback with per-install key generation (F-02).
4. Run `npm audit fix`; enforce `npm ci` (F-05).
5. Delete `themes.css.corrupted` and `=1.3.0` (F-16).

**Week 2 — Close the exposure**
6. Draft and publish the privacy policy; correct LICENSE attribution (F-04, F-18).
7. Pin dependencies with `pip-compile`; pin the git dependency to a SHA; add `pip-audit`
   to CI (F-06).
8. Rename themes off trademarked identifiers (F-09).
9. Move JWTs to httpOnly cookies, implement refresh-token rotation (F-07).
10. Replace `pickle` with `numpy.load(allow_pickle=False)` (F-13).

**Weeks 3-4 — Quality and platform**
11. Introduce the light/dark token architecture (F-11).
12. Accessibility pass: keyboard-reachable controls, contrast audit across all themes (F-12).
13. Ship the `.app` bundle wrapper for macOS camera permission (F-10).
14. Replace 218 `print()` calls with structured logging; eliminate bare excepts (F-14).

**Ongoing**
15. Coverage gates — start by measuring, then ratchet: 60% overall, 85% on `auth.py`,
    `crud.py`, and `camera_manager.py`. Fail CI below threshold.
16. Split modules exceeding ~800 lines (F-15).
17. Observability: structured JSON logging, `/health` liveness plus `/ready` readiness,
    Prometheus metrics for camera uptime, frame rate, and detection latency. Ship an
    opt-in-only crash reporter — a surveillance product must never transmit frames or
    biometric data off-device without explicit consent.

### Beta rollout

Gate beta on: tests green in CI without `continue-on-error`, zero critical/high npm
findings, privacy policy published, and a clean install-then-uninstall verified on a fresh
macOS machine and a fresh Raspberry Pi.

Then stage it — 5 internal installs for a week, 25 friendly external users for two weeks,
then open beta. Instrument install success rate, first-camera-added rate (the metric this
audit's originating bug would have driven to zero), and crash-free session rate. Because
`KeepAlive` is set on the launchd agent, a crash-looping backend restarts silently and
forever; alert on restart frequency or beta failures will be invisible.
